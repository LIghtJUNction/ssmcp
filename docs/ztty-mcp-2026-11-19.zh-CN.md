# 用真实 MCP 连接 ztty

## 本次实现

`ssmcp --shell ztty` 现在可以通过 ztty 的 MCP 服务建立终端，并打开一个可以正常输入的 X11 窗口。ssmcp 的终端工具和这个窗口使用同一个 PTY；窗口中的 Shell、进程号和原生会话身份没有再复制一份。该功能仍在本次功能分支，本文不表示已安装或部署 ssmcp。

协议实现使用固定版本 `zmcpio = 0.4.0` 的客户端状态机，实际完成 `initialize`、`notifications/initialized`、分页 `tools/list` 和 `tools/call`。Tokio 层负责有界管道、并发请求、取消及进程清理。没有把 Shell 文本命令包装后称作 MCP，也不调用模型。[协议适配器](../src/backend/mcp_stdio.rs) · [ztty 适配器](../src/backend/ztty.rs)

当前要求 Linux、可用的 X11 `DISPLAY`、真正的命令 Shell，以及提供 `output_base64` 的 ztty。`SHELL` 不能再指向 ztty 本身。ztty 仍拥有窗口绘制、键盘输入和 PTY；ssmcp 负责授权后的工具调用与结果呈现。Wayland 原生窗口、Windows 和 macOS 的这个接入路径尚未验收。

## 如何使用

使用包含本功能的 ssmcp 构建，并保证 `PATH` 中的 ztty 支持无损读取字段：

```sh
ssmcp --shell ztty
```

账户、服务器及 `--allow` 仍使用各自版本的正常配置。这个选项不会替代登录或扩大访问权限。没有图形环境或 ztty 缺少原始字节字段时，启动会给出明确错误；本次创建的窗口和私有服务会被清理。

在 `code_mode` 中先选中已有的目标客户端，发现实际注册的工具，再调用：

```javascript
const id = clients.find(c => c.name === "你的客户端名称").id;
const catalog = await tools.search(id, {
  name_prefix: "ztty.",
  include_schemas: true,
});
const sessions = await call(id, "ztty.session_list", {});
return { catalog, sessions };
```

工具名称加上 `ztty.` 路由前缀，描述、输入 schema、annotations 和真正的原生名称来自服务端目录。目录中的九项工具是：

| 工具 | 用途 |
| --- | --- |
| `ztty.session_create` | 按 ztty 原生语义创建会话 |
| `ztty.session_list` | 查询会话、PTY 与窗口状态 |
| `ztty.session_commands` | 查看会话命令记录 |
| `ztty.session_command_read` | 读取指定命令的输出 |
| `ztty.session_read` | 按字节游标读取原生输出和屏幕状态 |
| `ztty.session_write` | 向会话写入输入 |
| `ztty.session_resize` | 显式改变 PTY 几何尺寸 |
| `ztty.session_control` | 使用原生会话控制能力 |
| `ztty.session_close` | 关闭指定会话 |

`terminal.*` 兼容接口仍可使用。默认终端及通过 `terminal.open` 创建的终端会打开普通 ztty 窗口；直接调用 `ztty.session_create` 则保留 ztty 本来的行为，不额外承诺一个窗口。操作多个终端时传入真实返回的 `terminal_id`，避免依赖当前选择。[注册表](../src/registry.rs) · [终端管理](../src/terminals.rs)

## 为什么需要原始字节

PTY 输出是字节序列，并不保证每段都是完整 UTF-8 文本。例如，汉字可以被两次读取拆开，程序也可能输出 `0xff` 或 NUL。若先把字节转成有损字符串，再把字符串编码回 base64，原始数据就无法恢复。

本接入使用 ztty 的 `output_base64` 作为字节来源；兼容接口的 `data` 供人阅读，`data_base64` 保留实际字节。兼容接口单次上限仍为 32 KiB；原生 ztty 读取上限为 64 KiB，并可能多返回至多三个字节以结束 UTF-8 字符。兼容层会按自己的字节上限截取，并把游标推进同样多的字节。

另一个边界是有限缓存。假设缓存从 emoji 的中间开始，ztty 会跳过左侧不完整的 UTF-8 后续字节。此时 `first_cursor` 是缓存左边界，却不一定是返回字节的起点。适配器据此使用：

```text
返回字节起点 = native.next_cursor - 解码后字节数
兼容接口下次游标 = 返回字节起点 + 实际交付的字节数
```

这保持了原生游标坐标。若输出已被淘汰，兼容结果保留 `truncated`；后台归档标记不完整，并继续读取和显示后续内容。已丢失的字节不会被伪造为完整归档。此行为已有真实 256 KiB 保留窗口、截断到 UTF-8 字符内部的测试。

## 生命周期与边界

每个接入使用随机命名的私有 ztty broker，不接管用户已有的 broker 或终端。创建窗口使用普通 `ztty attach`，没有使用只读观察模式。会话调用携带 `uri`、`id`、`created_at` 和 `broker_pid` 的预期身份；陈旧身份拒绝写入。

窗口尺寸由 ztty 管理。ssmcp 仪表盘的布局变化不会偷偷改变它；显式 `terminal.resize` 和原生 resize 仍有效。`terminal.*` 管理的独立终端最多 16 个。创建、关闭及连接终止时只清理本接入拥有的窗口、PTY、服务和进程后代。[实现](../src/backend/ztty.rs)

客户端同时最多处理 32 个已发出的请求，另有 32 个有界排队请求；单帧最多 1 MiB，目录最多 32 页、512 个工具和 2 MiB 序列化内容。启动协商有 15 秒期限，普通调用有 45 秒期限，管道写入有 5 秒期限。长轮询不会占住唯一请求槽，响应按请求 ID 匹配。

未知响应 ID、超限帧、协议错误或调用超时会结束这条私有提供方连接，并清理其进程。已经提交的操作不自动重放；收到超时应先查看状态。服务器要求采样、交互续接或其他客户端回调时，本接入不会替它启动模型。原生工具的 `content`、`structuredContent`、`isError` 及服务端元数据保持原样；JSON-RPC 层错误仍作为错误返回。

## 验收证据

验证在私有 Xvfb 中进行，未操作用户的真实窗口。ztty 二进制来自源码 `f05dd2710c795412651f58839e28a345231445f6`，SHA-256 为：

```text
717487afce1e6c1588018654cbda70d1148fe7f5c22706220360d72678c5c39a
```

最终一轮源码前后哈希一致。四组测试合计 **19 项通过**，另通过 `cargo fmt --all -- --check` 和 `cargo clippy --all-targets -- -D warnings`。这不是全项目所有测试、所有操作系统或所有 MCP 服务器均通过的声明。

| 组别 | 项数 | 实际验证内容 |
| --- | ---: | --- |
| 独立 Python MCP peer | 4 | 分页目录、原生错误与元数据保留、回调拒绝、并发与乱序响应、请求超时和后代回收、坏 ID／超限帧关闭、无重放 |
| 原始字节游标 | 1 | UTF-8 左边界淘汰、实际字节起点和不一致游标拒绝 |
| 现有终端输入 | 13 | F7、Unicode、粘贴边界、独立终端路由、终端模式恢复等原有行为 |
| 真实 ztty 图形接入 | 1 | 原生九工具、普通可见窗口、同一 PTY／身份、二进制与 Unicode、单字节读取、真实淘汰边界、陈旧身份无副作用、副窗口关闭、尺寸所有权、最终窗口与进程回收 |

前两轮图形测试曾因测试机未安装 `xwininfo`、测试误用了兼容 API 之外的读取上限而失败；已分别改为直接查询 Xlib，以及使用兼容 API 的实际 32 KiB 上限。原始失败记录保留在本地验证目录，未计入通过数。最终成功记录与测试源可复核：[验证记录](reports/ztty-mcp-2026-11-19/validation.json) · [窗口结果](reports/ztty-mcp-2026-11-19/window.json) · [真实窗口图](reports/ztty-mcp-2026-11-19/window.png) · [测试代码](../src/backend/ztty/tests.rs)。窗口结果中已去掉临时输入所有者标识。

本次证明了协议、数据和生命周期的正确性，没有据此宣称 MCP 桥接吞吐高于直接 PTY，也没有把 ztty 的吞吐微基准套用到网络工具调用上。部署与整体性能测量另行记录。
