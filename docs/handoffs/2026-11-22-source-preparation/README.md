## 2. 为什么还不能宣布最终通过

当前输出留在所属客户端的内存中。默认保留期为 900 秒，后台清扫循环每轮等待 60 秒；公开读取、状态查询以及输出分配也可能顺便清理过期条目。因此，“读取时已不可用”不能单独证明后台清扫实际执行过。[存储实现](https://github.com/LIghtJUNction/ssmcp/blob/6759712e1b51f83690580897aee7efb01ac32f86/src/output.rs)

旧场景通过修改磁盘文件时间并观察 5 秒来加速过期条件。它从未证明自然等待了一整天，也不能据此新增自然等待 900 秒的要求。现在需要在测试构建中老化真实 RAM 条目，并分别保存公共读取结果与实际定时清扫的因果证据。

本轮已完成源码可行性设计，详细说明见 `expiry-fixture-design.md`。该设计尚未实现、编译或运行；现有普通 Rust 过期单测也不能替代尚缺的公共路径与定时清扫覆盖。

## 4. 接续顺序

1. 接收两个固定候选、独立评审结果和过期 fixture 设计，确认唯一集成负责人。
2. 明确新增测试接缝与时间安排：保留 900 秒生产 TTL 和 240 秒整体预算；70–75 秒单场景等待需要明确调整原 5 秒观察范围，保留 5 秒则需要额外的真实周期对齐。
3. 实现并独立复核公共路径过期／定时清扫覆盖，保持当前缺项导致非成功退出的结果，直至有实际证据。
4. 冻结统一源码，运行唯一的完整 CI，取得实际成功的构建产物、原 manifest、源码索引和报告。
5. 绑定本机消费者并执行剩余范围，核对进程清理、帧与报告，再填写最终结果和发布状态。
