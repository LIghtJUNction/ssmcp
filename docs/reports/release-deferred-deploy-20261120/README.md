# Defer a production switch while managed jobs are active

A normal release still publishes and deploys by default. An explicit main `workflow_dispatch` can set `deploy_server=false` to publish a verified immutable tag while holding production at its existing version. Build-only runs never enable deployment. The current main workflow selects deployment after tag validation, using only the verified `publish` result. It does not depend on a new output from the selected tag, so retrying an older immutable tag retains the same default and explicit-false behavior. This option does not weaken version, main-ancestry, recursive-submodule, archive, registry or runtime gates.

Use this only when the production switch has a concrete handoff constraint. Existing SSMCP clients may cancel native managed jobs when their relay connection closes; watchdog reconnect alone does not preserve the workload. Collect a read-only active-job snapshot and obtain the affected workload owners' checkpoint/normal-completion handoff. Do not stop their jobs to clear the gate.

When pushing a tag whose validated main commit has `[skip ci]`, first inspect the tag's workflow runs, then explicitly dispatch the Release workflow on main with the exact existing tag and `deploy_server=false`. The skip instruction must be in the target commit message, not merely the annotated tag message. Check that no queued or running automatic publication run is scheduled to deploy: release concurrency serializes runs and does not cancel or change another run's deployment choice. GitHub documents skip instructions for push-triggered workflows: https://docs.github.com/en/actions/how-tos/manage-workflow-runs/skip-workflow-runs . Ordinary tag pushes retain their existing automatic deployment behavior.

After assets are published, keep production status explicitly pending in the report. Once the safe switch handoff is available, use the existing Deploy server workflow with the exact published stable tag and source commit from `release-manifest.json`. Its production environment, deployment concurrency, staging health checks, digest checks and rollback procedure remain in force. Verify the resulting deployment receipt and client reconnections separately from publication.

Local validation executes the current workflow's inline deployment policy with private event and output files. Eight added tests cover old-tag output compatibility, exact Boolean and string choices, automatic tag defaults, build-only denial, malformed inputs, invalid publication outputs, and append-only output handling. The original 73 publication checks and 20 deployment checks remain in place. No Rust product source or dependency pin changes.

Actual local results: 81 publication/policy tests passed in 3.127 s, 20 deployment tests passed in 0.031 s, and `git diff --check` passed. The inline policy ran in child Python processes with private event/output files. Private raw logs are retained under `.local/release-deferred-deploy-20261120/`; no workflow was dispatched and production was not changed.
