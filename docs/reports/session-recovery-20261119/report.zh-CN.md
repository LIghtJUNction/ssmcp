# 会话恢复与保存容量：本机验证记录

本阶段已实现主动恢复索引和保存会话容量准入，并在隔离的本机测试中通过 26 个不同测试、格式检查及严格 Clippy。源码已推送，尚未安装到正在使用的 ssmcp，也没有重启服务或用户会话。

## 恢复之前做过什么、停在哪里

`history.recover(clientId)` 对应原生工具 `ssmcp.client.recover`。它把当前 Runtime 身份、正在记录的 JSONL 对话、已保存检查点、当前或最近任务状态、审计游标和输出引用放进最多 32 KiB 的结构化索引。最近记录默认 8 条，最多 16 条，每条预览最多 512 字节；需要正文时，再按真实消息 ID、下标或 artifact ID 分页读取。

调用不会重新执行旧命令、启动模型、切换对话或把历史文字放入待发送用户队列。未初始化的历史和检查点返回明确的不可用状态；单纯查询不会创建新的历史目录。不同来源分别取快照，因此任务结束或新消息写入仍可能发生在两次读取之间。Runtime 代次、进程代次、relay client ID 和持久 conversation ID 保持各自含义，不能用同名目录猜测同一活会话。

具体原语、分页方式和身份边界见[使用说明](../../session-recovery.zh-CN.md)。实现阶段为 [93b728e](https://github.com/LIghtJUNction/ssmcp/commit/93b728ea73b31d5803aee043efcbcd095e05b6ab)。

## 限制增长，保留已有工作

恢复索引直接引用已有数据，不另存一套聊天、附件、任务输出或审计正文。对话、输出和单个检查点继续使用原有预算；补上了检查点目录的新建准入：最多 256 个工作区，检查在跨进程文件锁内进行。达到上限后，已有工作区仍可在自身预算内读取和更新，新工作区得到明确错误。

保存会话也补上两个创建门槛：最多 1024 个已提交或中断准备目录，执行映像合计最多 4 GiB 逻辑字节。检查、复制和提交受已有管理锁保护；复制过程中也检查剩余字节，防止源文件变化导致越界。两名创建者竞争最后一个名额时，只有一个成功。

旧记录及正在运行的会话不会被自动删除、迁移或终止。原有无分页枚举的 1024 条保护仍然存在；旧存储本来超过该数量时，可按已知名称管理，不会静默返回截断列表。4 GiB 是执行映像预算，不是整个用户目录的物理空间保证，也不包含编译缓存。容量改动见 [53794fe](https://github.com/LIghtJUNction/ssmcp/commit/53794fe4f914aa6c75737d9c0a1836e9c47d1ca3) 及[存储说明](../../session-storage.zh-CN.md)。

验证时仅读取本机保存目录的元数据：2 个保存目录、2 份执行映像，逻辑长度合计 19,781,728 字节，已分配块合计 19,783,680 字节。没有读取其中的会话正文、配置内容或附件。

## 验证边界

本轮运行平台是 Linux x86_64。原生恢复在自有隔离 Runtime 中执行，Node helper 通过内存协议 peer 验证，没有将它描述为已安装 relay 的线上验收。Windows 和 macOS 未运行本轮测试。4 GiB 案例使用自有稀疏文件验证真实逻辑长度门槛，没有写入 4 GiB 测试正文。

开发机保留原始日志、源码快照和哈希清单；公开材料只含合成测试结果、统计及代码，不含用户窗口截图、聊天或附件。下一步由整合任务合并到最终候选，再按其部署范围验收；本阶段未发布、安装或重启 ssmcp。
