# 等待用户：双端整合与通知验收

已将服务端等待协调器、原生终端等待 UI 和通知模块合成一个可运行候选。63 个不同 Rust/Node 测试、真实 PTY 流程的 119 项断言，以及私有 DBus 上的 4 个通知场景均通过。源码已经提交；本阶段没有安装、发布或重载正在使用的 ssmcp。

## 复用现有实现，打通同一个交付过程

候选从 main `46c6463` 出发，保留合并了 UI 分支 `4de90fd` 和协调器分支 `4f35eeb` 的来源历史。本轮增加实际通知验收，修正窄屏回归的测试预期，并完成统一客户端与服务器验证，没有再建立一套等待队列。可审阅[整合提交](https://github.com/LIghtJUNction/ssmcp/commit/e9b83a3367940d7bd8b1a77bdc853a22f6bbe9d6)。

在 `code_mode` 中，调用者主动执行：

```javascript
return await ui.wait(clientId, {
  timeout_ms: 20000,
  intent: 'need_user',
  reason: '请确认接下来要处理的文件。',
  notify: true,
});
```

外层 `code_mode` 的超时要覆盖等待和交付开销，例如 30 秒。一次等待接受 1–25 秒，默认 20 秒；需要继续等时，在新的外层调用中再次执行。它不会启动模型，超时也不表示用户同意结束。准备结束时可以用 `intent: 'finish'` 明确提出确认，但参数本身不是同意。

等待预约现有普通用户队列中的具体消息版本。服务端在最终响应前重新检查实际身份、客户端访问权限和绑定的 agent，再提交那些仍然有效的版本。只有外层 `structuredContent.user_wait` 中的 `received` 与同一响应 `user_messages` 的消息 ID、revision 相符，才说明这次交付已经提交。脚本内的 `ready` 只是预约，不是正文交付；取消、断线和过期不会把预约转换为已收到。

显示名称不能授予身份。未绑定的调用者只能领取 Next caller 消息；指定 agent 的消息必须通过真实绑定。普通等待、跨会话候选 inbox 和 `/send` 监听程序保持各自用途。完整合同见[等待用户输入](../../user-wait.md)。

## 终端与通知

活动等待在输入框下方提供简短提示；存在未提交草稿时仍可见。`/wait` 显示目标、原因、编号和状态，`/wait cancel <编号或唯一前缀>` 只取消该等待，保留草稿和其他队列。四个原生活动等待及最近 32 个完成记录都有上限，连接换代不会继承旧等待。

通知通过系统助手提交。相同等待 episode 去重，通知器只保留最近 128 个摘要，并设置 60 秒冷却。`sent` 只说明通知请求已提交，`user_seen` 始终是 `null`。无法通知不会伪造成功，也不妨碍用户在终端取消等待。

Linux 真实验收使用已安装的 `notify-send` 和真实 DBus IPC，接收服务位于自有私有总线；客户端环境移除了宿主桌面地址，没有给用户桌面发送测试通知。该夹具确认了四件事：真实提交得到回执；相同 episode 不重复提交；缺少助手有明确不可用状态且仍可取消；取消真实等待后，自有阻塞助手及其后代不再运行。它不声称用户真的看见了桌面通知。

## 本机结果

| 检查 | 结果 |
| --- | --- |
| 等待、认证及最终提交、取消竞争 | 27 个不同测试通过 |
| 通知参数、去重、超时和取消 | 8 个不同测试通过 |
| 原普通 steering 队列回归 | 25 个不同测试通过 |
| observation 分类 | 1 个测试通过 |
| 真正执行的 Node context helpers | 2 个测试通过 |
| 格式、严格 all-targets Clippy、客户端/daemon/VT decoder 构建 | 均以 0 退出 |
| 统一客户端与真实账户路由器的隔离 PTY | 119 项断言通过 |
| 私有 DBus 通知 | 4 个场景、74 项断言通过 |

两组端到端断言包含重复的初始化检查，不当作额外的 193 个不同 Rust 测试。原 PTY 验收覆盖精确接收者、三条同时等待、容量拒绝、未提交的 Unicode 多行草稿、Next caller 与指定 agent 的实际交付、超时、取消、断线重连、凭据不出现在终端输出，以及自有 termios 恢复。

验收客户端 ELF 为 `c445b0da7524a293de265b0c4decb76251b7c77ad2621041812342c16358d374`。账户路由器 fixture、daemon 和独立 VT decoder 也分别记录了哈希，所有二进制在端到端验收前后相同；测试期间源码快照指纹前后也一致。详见[机器汇总](validation.json)、[PTY 结果](real-pty.json)和[通知结果](private-notifications.json)。

两次测试配置修正均保留了原日志：窄屏断言原先要求 48 列仍显示已被原布局省略的快捷键文字，现改为核对加入等待前后原控制提示一致，120 列仍检查快捷键；context helper 首次缺少 `--ignored`，没有真正运行测试，被门禁拒绝后才显式运行两项并通过。没有把跳过写成通过。

真实 VT 文字快照可查看[120 列等待](active-120.txt)、[48 列超时](timeout-48.txt)及[通知提交后的终端](notification-submitted.txt)。对应脚本是 [PTY 验收](../../../scripts/e2e_user_wait.py)和[通知验收](../../../scripts/e2e_user_wait_notifications.py)，均只操作自有临时会话。

## 实际边界

运行验收平台为 Linux x86_64。Windows、macOS 的通知参数构造参加了单元测试，未运行这两个系统的原生通知集成。MCP 能观察明确的等待调用和本地答复信号，不能拦截所有外部模型的最终回答，也不会把 agent 提供的字段当作用户同意。

原始日志、失败尝试和合成 VT 数据留在开发机证据目录；公开文件不含用户聊天、附件或真实窗口。没有为归档再复制数百 MiB 的调试二进制。接下来由总整合任务合入最终候选；本记录不把分支通过验收说成已经部署。
