# ssmcp 多会话互联：先固定目标，再执行能力

状态：设计建议，尚未宣称联邦连接器或下列新 API 已实现。日期：2026-11-19。

## 目标与判断

用户希望 agent 通过主 ssmcp 的 `code_mode`，调用另一个 ssmcp 的 MCP，必要时调用对方的 `code_mode`。核心问题是每次调用都能回答三个问题：在哪个服务、哪个业务会话执行；谁授权了它；失败后能否安全重试。

建议把远端 MCP 挂载成显式目标，提供带目标的普通工具调用和显式远端编排两种操作。模型不必反复拼接嵌套脚本、转义参数和猜测目标；内核负责固定身份、校验目录版本、记录来源和传递取消，MCP 连接器插件负责协议适配。

先区分两种情况。如果 A、B 已经都出现在同一账号的 `clients` 列表，直接使用 B 的精确 `client_id` 和现有 `call(B, name, args)` 即可。如果主 ssmcp 必须连接另一个独立 MCP endpoint，才需要新的远端连接器。两种情况可以共用一套目标句柄，但不需要强迫第一种情况额外绕一次网络。

## 一、身份必须分开

| 身份 | 回答的问题 | 规则 |
| --- | --- | --- |
| `mount_id` | 主 ssmcp 中配置了哪个远端连接 | 本地生成并绑定实际 endpoint、授权配置；名字只是标签 |
| `server_id` | 对端是哪个经过验证的服务 | 不能把 `serverInfo.name` 当唯一身份；第三方无稳定身份时由挂载配置固定来源 |
| `session_id` | 在哪个 ssmcp 业务会话内工作 | 与标题、工作目录、操作系统 PID 分开；目标必须精确 |
| `connection_epoch` | 这还是之前观察到的那次连接吗 | 重连后递增或更换，旧句柄拒绝执行；需要显式重新解析 |
| `catalog_revision` | 当前工具合同是否仍相同 | 发现后缓存；变更时拒绝过期调用并刷新，不静默调用替代工具 |
| `operation_id` | 这是哪一次逻辑操作 | 用于查询回执和应用级去重；不同于每跳 JSON-RPC request ID |

公开句柄应是服务端产生的不可伪造引用，而不是让模型自行组装上述字段。模型能看见安全的目标摘要；endpoint 凭据和委托 token 留在内核。获取句柄并不免除每次调用时的权限校验。

MCP 规范明确指出：工具名字只在单个服务内唯一；聚合多个服务需要消歧，`serverInfo.name` 也不保证唯一。[1] ssmcp 已支持 MCP 2026-07-28 和 2025 系列；设计必须同时适配它们。2026-07-28 的协议核心已取消隐式协议会话，应用状态通过显式句柄关联。[2] 因而 ssmcp 的业务会话身份不能寄托在某个传输层 session header 上。

## 二、推荐的使用方式

以下是拟议 API，当前不能直接当作已提供工具运行：

```javascript
// 解析必须恰好得到一个目标；同名、离线、权限不符均明确失败。
const target = await remotes.resolve({
  mount: "home",
  session: { id: "session-videos" }
});

// 通常只需要一条带目标的工具调用。
const result = await target.call("ssmcp.fs.read_text", {
  path: "README.md",
  max_bytes: 8192
});
```

工作目录是目标会话中的上下文，不是用来挑选会话的唯一键。`Videos` 下有两个连接时，应返回 `AMBIGUOUS_TARGET` 并列出候选，而不是取列表第一个。连接已离线则返回 `TARGET_OFFLINE`，不能偷偷寻找同名替代者。

确实需要在远端连续处理多个步骤时，再使用显式远端编排：

```javascript
// inputs 是数据；code 是唯一一层由调用者写的脚本。
// 远端执行上下文绑定 target，只开放已授权的目标能力。
const result = await target.codeMode({
  code: "const r = await target.call('ssmcp.fs.read_text', inputs); return r;",
  inputs: { path: "README.md", max_bytes: 8192 }
});
```

这要求连接器给远端运行建立明确的绑定上下文，并在远端每次调用时检查目标和权限。不能只把一个 `client_id` 字符串塞进上下文，再允许脚本任意切换成其他身份。**现有 ssmcp 并未提供这项单客户端委托约束**：远端 `code_mode` 仍可见该 OAuth 身份能访问的全部客户端。第一版应只允许固定的指定客户端桥接；若保留任意远端脚本，接口必须明确为端点范围，不能称作已限制在一个客户端内。

如果对端目前只暴露 `list` 和 `code_mode` 两个 MCP 工具，第一版适配器内部仍可能通过对端 `code_mode` 转发。适配器应使用固定、经过测试的桥接模板和结构化参数，隐藏这层机械工作。模型层提供统一 `target.call`；后续可以换成专门的数据转发入口而不改变调用者接口。普通 MCP 服务则直接执行标准 `tools/call`。

## 三、结果必须保留来源和原始类型

建议返回由内核生成的来源信封和完整 MCP 结果：

```json
{
  "origin": {
    "mount_id": "mount-home",
    "session_id": "session-videos",
    "connection_epoch": 7,
    "operation_id": "op-example",
    "route": ["main", "home"]
  },
  "result": {
    "content": [{ "type": "text", "text": "example" }],
    "structuredContent": { "example": true },
    "isError": false
  }
}
```

来源由可信路由层附加，不能接受对端结果中自称的身份来覆盖它。文本、图像、音频、资源链接、结构化结果、`isError` 和协议继续交互所需的不透明状态都要保持其语义；不能只留下第一段 `content[0].text`。[1] 对外日志可脱敏，对协议需要的私有状态则存为不透明回执，不向模型暴露凭据。

文件路径、输出 ID 和资源 URI 必须绑定来源。B 返回的 `/tmp/a.png` 只能在 B 的上下文解析。读取远端资源通过同一目标句柄；任何显式文件传输都应作为单独能力，不根据一个同名路径自动在主机查找。远端 `user_messages`、协作回执和分页游标同样保留来源，不能并入主会话队列后自动确认。

终端为跨节点操作显示简短目标，例如“主会话 → home / Videos · connection 7”，并支持查看完整来源。短标签用于阅读，完整身份用于动作。日志不能用标题或工作目录拼成假身份。

## 四、超时、取消与重试不能混为一谈

一次调用使用共同的剩余时间预算。转发只消耗预算，不能在每一跳重新获得完整超时时间。每跳维护 request ID 映射；原始 `operation_id`、父调用关系和追踪 ID 连续保留。

取消由连接器按协商版本适配。2026-07-28 的 stdio 使用取消通知，Streamable HTTP 通过关闭对应响应流表示取消；2025 系列有独立取消通知语义。[3][4] 内核暴露统一取消能力，而不是要求所有传输硬编码同一个消息。

取消请求也不等于已撤销副作用。远端可能已完成写入，只是回执未回来。因此错误至少区分：

| 状态 | 能确认什么 | 后续动作 |
| --- | --- | --- |
| `NOT_DISPATCHED` | 操作尚未提交到远端执行 | 修复目标或权限后可重新提交 |
| `COMPLETED` | 收到了完整结果 | 使用同一回执，不再执行 |
| `CANCEL_REQUESTED` | 已向目标传递停止意图 | 查询最终状态，不直接宣称已停止 |
| `OUTCOME_UNKNOWN` | 请求可能已经执行，但没有确定结果 | 用 operation/job 回执查询；有副作用的操作不自动重放 |

可读取的操作也不应只凭一个来自不可信服务的 `readOnlyHint` 就无限重试。MCP 把 annotations 视为提示；其可信度取决于服务。[1] 自动重试策略应由明确的工具合同和预算控制。对于写入，接收端可以实现持久的 `operation_id` 去重记录，但应说明保留期限、参数不匹配冲突和崩溃恢复范围，不能声称任意外部副作用都可做到严格只执行一次。

ssmcp 已有独立执行作业。结束某次 `code_mode` 不应默认销毁其返回的长期 job。取消编排、取消一个在途 RPC、终止 job 是三种操作；涉及多跳时仍应明确保留这种区别。MCP 的任务扩展也把 task cancellation 与普通请求取消分开，而且承认取消是协作式的。[5]

## 五、权限、循环和资源边界

原始用户身份、转发服务身份和显示用 controller 名称分开记录。每一跳使用该服务认可的凭据或正式支持的委托机制；不能把主服务收到的 bearer token 原样传给别的 audience，也不能让脚本自称另一个用户。

路由层限制最大跳数，拒绝默认路径中重复的服务节点；只允许显式配置和授权的 mount。第一版宜采用单跳桥接，不自动导入远端的其他上游。任意远端脚本的递归约束需要双方协商并执行不可由脚本重置的委托上下文；本地检查几个工具名或 URL 不能证明对方不会再调用回来。超时预算、并发数、队列长度、返回字节数和资源保留时间都要有界，错误应指出是哪一跳达到限制。共享连接池和能力目录缓存以认证主体、挂载和版本为键，避免跨账号复用私有目录或结果。

## 六、与两层插件化的对应关系

| 层 | 负责的合同 |
| --- | --- |
| 内核 | 目标句柄、权限、连接代次、路由链、操作回执、取消与预算、审计、资源来源 |
| MCP 连接器插件 | 连接/发现、版本适配、目录刷新、`tools/call`、进度与取消翻译、结果传递 |
| Files / Desktop / Process 等能力插件 | 自己的实际能力状态、执行、资源清理 |

后两项同属插件层，没有另造第三个中心。zplugin 的 ABI 解决进程内边界；跨服务调用仍通过 MCP 网络协议，两者各自完成自己的工作。现有原生 NativeHost 属于单个客户端连接，当前服务端的 `call(client_id,...)` 只路由到自身 Broker；远端 MCP 不能伪装成它的本地客户端。连接器接入服务端受控 host 时，应添加独立的跨端点目标类型和授权合同，复用 ABI 的生命周期机制，不直接复用本地调用印记作为委托证明。该结论经过[当前 HTTP 路由源码](https://github.com/LIghtJUNction/ssmcp/blob/6510c2a2624ca0a656c3d14cd46e6771620d5955/src/http.rs)和[code_mode 源码](https://github.com/LIghtJUNction/ssmcp/blob/6510c2a2624ca0a656c3d14cd46e6771620d5955/src/code_mode.rs)核对。

## 七、与“强制发送”的关系

工具路由和消息监听可以复用目标身份、回执、取消、审计等底层合同，但它们处理的对象不同。强制发送需要显式单监听者 lease：一个业务会话同时最多一个活跃监听者；无监听者立即返回 `NO_LISTENER`。普通一次 `code_mode` 拉取消息不能自动成为长期监听者。

“已入队”“监听者已领取”“已转交模型服务”“模型已回复”是不同状态。当前新增能力应提供监听、投递和确认的扩展点，不虚构尚未实现的主动模型调用。监听租约过期后，旧监听者不能确认新代次的消息；网络断开导致结果未知时，通过 delivery ID 核对，避免重复提交同一用户消息。

## 八、并行调用如何显示

建议用一个任务组包含多条独立子任务，父行显示目标和“已完成 2/4”，每个子项显示用途、状态、耗时，并保留独立输出区域。低对比竖线只表示共同归属；子任务之间的箭头只用于真实依赖，不把并行关系画成执行顺序。窄终端仍保持纵向布局，详细时间轴放在展开视图。

| 显示信息 | 应使用的运行数据 |
| --- | --- |
| 属于哪个任务 | `parent_run_id`，不能用相似标题猜测 |
| 点击或取消哪一次调用 | 完整 `call_id`；界面可显示短编号 |
| 是否实际重叠执行 | 真实开始/结束时间；`Promise.all` 本身不构成证据 |
| 哪些调用构成一次显式并发组 | 可选 `parallel_group`，由编排上下文提供 |
| 是否已有确定结果 | 运行、成功、失败、取消已请求、结果未知分别显示 |

子项开始后保持稳定位置，完成时更新状态，避免重新排序导致点击错位。默认展开正在输出、失败或用户选中的项，已完成内容可以折叠。父编排结束与独立后台作业结束仍然分开。这里是显示方案；本轮已经实现的基础是独立命令面板和内建插件的并发轮询，不宣称新的并发任务组界面已经完成。

## 实施次序与验收

先统一单 broker 内的显式目标句柄，再做独立 endpoint 连接器，最后添加必要的远端多步编排。第一版应验证：同名同目录目标消歧、连接重建拒绝旧句柄、跨账号拒绝、嵌套循环拒绝、剩余预算递减、取消传播、写入后断线不自动重放、图像和错误原样传递、远端文件来源不丢失、独立 job 生命周期，以及无监听者立即失败。

这些验收属于联邦功能设计计划，不计入本次已通过的插件或界面测试数量。
