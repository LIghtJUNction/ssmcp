# Computer Use 的系统权限边界：后续设计草案

**状态：设计建议，尚未实现或运行验证。** 本文回应 agent 通过 Shell、独立程序或本机开关绕过 Computer Use Off／控制额度的问题。当前 SSMCP 的统一开关约束应用入口，`os_permission_boundary=false`；本轮源码与验收仍按[本轮阶段报告](README.md)推进。本文不作为第 16 轮验收的新条件，也不代表已经配置生产账户或桌面隔离。

## 目标从权限开始

程序能连接哪些服务、持有哪些文件描述符、能修改哪些状态，决定了它实际能做什么。只要 agent 及其子进程仍有直接控制桌面的权限，应用中的开关就无法覆盖所有控制路径。

拟议目标是：**在已确认的系统配置和通道范围内，受限 agent 及其全部后代只能通过受控执行服务取得桌面控制能力，不能自行开启控制或重置额度。** 这里的 broker 指持有实际桌面权限、核验请求并执行获准动作的服务。内核、受信任的启动器、broker、管理入口和受保护状态构成可信范围；agent 的代码、Shell、插件和子进程都按不可信请求方处理。

同 UID 并不必然无法隔离，但 UID 相同也不能证明请求来自可信管理入口。若采用 Landlock 一类强制约束，必须在运行不可信代码前建立域，并覆盖全部执行路径；其规则由后代继承，而给一个线程施加规则不会自动约束已经存在的其他线程。[内核继承与进程访问规则](https://docs.kernel.org/userspace-api/landlock.html#inheritance)

## 拟议结构

受信任的启动器先验证所需系统能力和实际策略，再启动受限 agent。broker 留在独立、受保护的执行域中，持有真实桌面连接；它只接收限定资源、限定动作的结构化请求。人工管理入口可以修改 On/Off 和预算，普通动作入口无此权限。两种入口需要可验证的身份区分，不能依赖调用者自报名称或把管理口隐藏在工具列表之外。

人工管理还需考虑已获准的桌面自动化：如果 agent 能点击管理界面，它也可能替用户操作开关。因此，开启控制、增加预算或改变策略应要求 agent 无法取得的独立管理会话，或无法由该桌面自动化代办的用户在场确认，并绑定获准的具体主体、范围、预算、期限与代次。仅证明请求来自某个 GUI 进程，不足以证明操作者是人。具体认证方式留待接口设计，不把普通点击或可被合成的快捷键当作这一证明。

实现可选择专用执行身份，或经过验证的同 UID 强制安全域。无论哪条路线，都需要同时约束文件、IPC、网络和继承资源。单独创建 UID、清环境变量或启动一个 namespace 工具，均不足以覆盖这份合同。bubblewrap 官方说明也将具体隔离策略交给构造参数的上层程序负责。[bubblewrap 策略边界](https://github.com/containers/bubblewrap/blob/main/SECURITY.md#sandbox-security)

| 实际能力通道 | 后续方案应建立的约束 |
|---|---|
| X11、Wayland、输入设备和桌面认证材料 | agent 无法直接取得受保护桌面的控制连接或所需权限；只向 broker 提交获准动作。是否具有全局输入权限按实际协议和系统配置判定。 |
| 已打开的 socket、设备、终端与其他 FD | 启动前清点并关闭非必要继承资源；broker 不把原始控制连接转交给 agent；后续 IPC 也不能重新泄漏等价能力。 |
| 宿主 D-Bus、服务管理器、通用执行代理 | agent 不能借此在约束域外启动进程。broker 的接口也不提供等价的任意宿主命令执行。 |
| CDP 等可控制浏览器的网络端点 | 按目标地址、端口、协议和认证能力限制可达性；保留业务联网时，代理规则不能重新开放宿主控制端点。 |
| broker 进程、配置、管理凭据及持久状态 | agent 不能读写敏感状态、注入可信进程或修改启动策略；管理凭据不进入 agent 的环境和可读文件。 |
| 观察与自有清理 | 使用限定资源的接口；观察授权和控制授权分别核定，清理只作用于该请求拥有的资源。 |

环境变量只是默认寻址方式的一部分。XOpenDisplay 接受显式地址；Wayland 既支持显式 socket 路径，也支持已有连接 FD。因此应直接控制这些资源，而不能把清空 `DISPLAY`／`WAYLAND_DISPLAY` 当作撤权证据。能够连接 Wayland 本身，也不等于具备任意全局输入注入权限。[XOpenDisplay](https://xorg.freedesktop.org/archive/X11R7.5/doc/man/man3/XOpenDisplay.3.html) · [Wayland 连接 API](https://wayland.freedesktop.org/docs/html/apb.html)

宿主 IPC 和终端同样需要纳入策略。bubblewrap 的限制说明特别列出经 D-Bus／systemd 重新执行命令及终端注入风险；内核文档也说明，部分约束不会追溯改变先前打开的描述符。[bubblewrap 限制](https://github.com/containers/bubblewrap/blob/main/README.md#limitations) · [描述符关联权限](https://docs.kernel.org/userspace-api/landlock.html#rights-associated-with-file-descriptors)

## Off 与额度的拟议合同

broker 保存可信主体、开关代次、预算和请求去重状态。预算作用域必须与经过认证的主体绑定，不能因换自报名称、重连或重启 agent 自动重置。这里讨论的是桌面控制预算；外部模型服务的计费额度仍由相应服务决定。

1. 接收请求时，在受保护状态中完成身份核验、资源授权、占额和请求登记；并发请求不能重复使用同一份预算。
2. 排队后的动作在实际派发前复核代次和撤权状态。Off 使尚未派发的旧请求失效，重新 On 不恢复旧票。需要明确并记录 broker 内的派发顺序，不能把检查与跨进程 I/O 宣称为天然原子操作。
3. 已经开始派发但没有有效结果的动作保留“未知或部分执行”，不能凭客户端断开自动判成未执行、退款并安全重放。去重记录和预算结算需要覆盖这一状态。
4. 正常结果、拒绝、撤权、未知结果以及自有资源清理分别记录。日志保留必要的请求归属和派发证据，避免收集无关桌面内容或认证材料。
5. broker 重启、持久状态损坏或隔离能力不足时，受保护模式应保持拒绝控制，并给出可诊断原因。兼容模式若存在，必须明确展示它仅提供应用内门禁，不能沿用系统隔离的保证。

以上是本项目的设计选择，不是官方文档对当前 SSMCP 的证明。浏览器调试通道尤其不能按普通网络连接处理；Chrome 官方将其与敏感浏览器数据访问联系起来，隔离 profile 也不能替代控制通道本身的授权。[Chrome 远程调试安全说明](https://developer.chrome.com/blog/remote-debugging-port)

## 后续实现与证明顺序

先确定受支持的系统组合和可信启动路径，再冻结具体策略、broker 接口与状态机。检测实际内核能力，逐项说明哪些权利由什么机制限制；安装了某个工具或某次拒绝返回值本身不能证明整套策略成立。Landlock 官方接口允许查询当前支持的 ABI，具体部署仍需按实际能力组合验证。[内核兼容性说明](https://docs.kernel.org/userspace-api/landlock.html#backward-and-forward-compatibility)

未来在专用测试桌面中保存二进制、策略、系统能力和身份配置，并同时取得两类证据：受限 agent 及其子进程对实际存在的直接桌面、IPC、网络、继承资源、管理状态与域外执行路径被拒绝；经过 broker 的获准动作能产生预期效果，而 Off、预算耗尽和旧请求重放不能新增动作。以 broker 的派发记录和桌面／浏览器效果核对结论，并验证观察、自有清理和崩溃恢复的规定行为。还应覆盖 agent 利用已获准的桌面动作操纵管理界面的路径，确认它不能因此扩展自身授权或预算。

可承诺的边界限于受支持配置中的受限 agent 域及其后代。管理员、未进入该域的宿主程序、内核漏洞，以及已经送达动作的不可回滚效果，均须按各自范围说明。本文没有运行上述验证，也没有把本轮应用内回归测试算作系统隔离证据。
