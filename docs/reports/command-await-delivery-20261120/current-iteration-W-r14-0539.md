| 范围 | 当前源码实现 | 这次仍待确认的部分 |
|---|---|---|
| 临时输出 | 普通 Unix 连接直接使用 `/tmp/ssmcp-<有效 UID>`，保留私有权限、UID 和链接检查；旧路径仅限受控 reload 兼容 | 报错进程是否执行该实现，以及实际版本、入口或兼容路径 |

| 本地状态与凭据 | 使用各自的 HOME/XDG 状态、配置和私有目录，按工作区区分历史与本地记忆 | 切换用户后的实际环境；原日志的本地记忆错误尾部本身已截短 |

Linux 的有效 UID 是进程当前所属用户的数值身份。临时资源按它分开，可以避免第二个用户碰到第一个用户拥有的共享私有目录。现有源码已采用这一方式；日志中的旧路径本身不能证明当前 W 缺少该处理，也不能证明用户运行的是哪个旧版本。

仓库已有 `scripts/test_multi_user_runtime.py`，覆盖两个 UID 的输出隔离和继承控制终端场景，并对应两个显式 ignored worker。本次只读确认了这些代码和覆盖边界，没有执行该驱动或更改用户目录权限。后续先核实实际运行身份，再记录针对性执行结果。这个操作系统用户问题与下面的 HTTP 跨 subject 断言分别调查。

## 首次收件人查询的产品修正

原会话分组验收会在登记收件人后立即按精确 ID 打开选择器。U 的第二轮界面验收在这一步停下：界面提示没有匹配的已验证收件人，草稿被保留；实际的会话分组操作尚未开始。

服务端登记结果与终端当前持有的目录副本是两个状态。查询到来时，终端的副本可能还未包含新收件人。产品需要保存本次查询，等待与它关联的目录请求完成，再处理结果。

V 以对应请求的回执判断完成，目录内容没有变化也能识别请求已结束；连接变化时，旧连接的结果不会用于新连接的查找。V 也处理了一个更细的时序：本次查询可能复用一个已经在途的目录请求，而该请求取得的数据早于本次查询。若旧结果没有匹配项，V 最多再等待一次查询后创建的目录请求；请求 ID 边界和原连接共同确定该结果是否属于本次查找。新结果仍无匹配时，查找结束并保留草稿。

| 当时状态 | V 中实现的处理 | 保留的用户意图 |
|---|---|---|
| 当前目录副本没有目标 | 保存明确查询，等待关联的目录结果 | 保留原草稿和光标状态 |
| 复用的旧请求返回无匹配 | 最多使用一次查询后的新请求确认 | 给首次查询取得新结果的机会，并限制等待次数 |
| 结果中有精确匹配 | 打开选择器并高亮已验证的对应行 | 发送仍需要明确操作 |
| 新结果仍无匹配，或对应请求失败 | 结束等待并显示相应提示 | 保留草稿 |
| 等待期间取消、导航、编辑草稿或输入新查询 | 让后来的操作优先于迟到结果 | 保持用户当前选择及输入状态 |

本次修正针对非空的明确查询。空查询遇到空目录时，现有行为仍是发起刷新并提示重试。

以上实现在 V 阶段通过库回归检查，并通过保留原脚本的首次查询与会话分组验收。W 首轮尚未执行会话分组套件；完整界面及 P1 范围继续按各自实际结果记录。源代码与用例范围见 [V 源码事实表](source-V2-push-public-facts.json)，界面结果见 [V 本轮界面事实表](ui24-V-composer-attempt-public-facts.json)。
