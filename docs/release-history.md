# 历史版本的构建来源与清理后的源码

Git 提交号包含目录内容及父提交信息。移除历史截图、视频或压缩报告后，提交号会变化；这不表示已发布的程序重新编译过。

部署工具分别记录 `build_commit` 和 `source_commit`。前者仍是原 Release manifest 中的实际构建提交，后者是经过附件清理的源码提交。返回记录中的 `commit` 保持源码定位含义。

## 接受历史来源映射的条件

普通版本继续要求 manifest 的构建提交与请求的源码提交完全一致。只有仓库内置的五条已审映射允许两者不同；Release 元数据、命令参数和环境变量都不能添加例外。

每条例外固定仓库、版本标签、原构建提交、清理后源码提交，以及原 manifest 完整字节的 SHA-256。映射还固定旧、新目录树及保留条目指纹、删除路径清单指纹和审计文件指纹。内置表本身也有固定的 canonical SHA-256。任一项不匹配都会拒绝该来源。

## 部署与历史重现的边界

部署历史版本时应使用包含这些固定映射的新版部署 helper。历史标签中的旧 helper 不回填新代码，它仍按当时的严格提交相等规则工作。新版 helper 在接受来源映射后，继续执行原有归档校验、runner 与资源比对、版本降级保护、隔离验证、启用和回滚检查。

原 Release manifest、已发布归档及其校验值保持原始来源。新版部署回执会明确记录 `artifact_rebuilt: false`，不会把旧资产说成新提交的构建结果。

从清理后的标签下载 Git 源码归档或重新打包源码，其字节会发生变化。部分较早版本的 Makefile 曾用固定 JPG/PNG glob 安装文档，移走附件后该旧安装规则可能失败；当前分支使用递归复制文档的规则。保留源码内容相同不等于每个历史打包流程都不受附件移除影响。
